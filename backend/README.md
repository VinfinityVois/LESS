# LESS Backend

## Зашифрованное хранилище

Backend использует SQLCipher 4 для шифрования **всего файла SQLite**: таблиц сотрудников, NFC UID, журналов проходов, учётных записей администраторов, сессий, аудита, гостевых пропусков, согласий и биометрических данных. Шифрование отдельных фотографий и шаблонов AES-GCM остаётся дополнительным уровнем защиты.

### Первый запуск

1. Остановите все процессы backend и сделайте резервную копию каталога `backend/data` на зашифрованный носитель.
2. Скопируйте `.env.example` в `.env`.
3. Если в базе уже есть биометрия/фотографии, **сохраните ровно тот SECRET_KEY, которым они были зашифрованы**. Не генерируйте новый. Если персональные биометрические данные ещё не сохранялись, создайте новый уникальный ключ:
   ```powershell
   python -c "import secrets; print(secrets.token_hex(32))"
   ```
4. Вставьте новый результат как `SECRET_KEY=<64 hex символа>` в `backend/.env`, только если прежнего ключа не было и биометрии ещё нет.
5. Сохраните ключ отдельно от базы и зашифрованных резервных копий. Не добавляйте `.env` в Git, облачные общие папки или логи.
6. Установите зависимости из `requirements.txt`.
7. Скачайте официальный локальный файл модели проверки лица:
   ```powershell
   python scripts/download_models.py
   ```
8. Запустите backend. Без файла `backend/models/face_landmarker.task` liveness-проверка завершится безопасным отказом с понятной диагностикой.

### Миграция существующей базы

При старте backend проверяет файл `data/skud.db`. Если обнаружена обычная SQLite-база, SQLCipher создаёт зашифрованную временную копию, проверяет открытие ключом и `PRAGMA integrity_check`, сохраняет дополнительную **зашифрованную** резервную копию рядом с БД и атомарно заменяет исходный файл. Если проверка или экспорт не проходят, backend останавливает инициализацию, а исходный файл не заменяется. Не запускайте два экземпляра backend во время миграции.

После миграции:
- файл базы и резервная копия открываются только с прежним `SECRET_KEY`;
- администраторская авторизация использует тот же SQLCipher-коннектор и ту же зашифрованную базу;
- неверный или отсутствующий ключ приводит к отказу запуска, а не к созданию пустой базы;
- для восстановления требуется исходный ключ и проверенная резервная копия.

**Ключ нельзя менять вручную после миграции.** Для ротации нужен отдельный план: резервная копия, экспорт старым ключом, импорт новым ключом, проверка целостности и тест восстановления. Потеря ключа означает потерю доступа ко всем данным.

### Важное ограничение удаления старого plaintext

Миграция не создаёт новую незашифрованную резервную копию. Однако атомарная замена файла не гарантирует физическое затирание старых блоков на SSD, в снапшотах, теневых копиях, резервном ПО или синхронизируемых папках. Для производственной установки включите полнодисковое шифрование ОС, ограничьте ACL каталога `backend/data` и проверьте/удалите прежние plaintext-копии по политике хранения. Резервные копии SQLCipher также требуют сохранения ключа отдельно.

SQLCipher защищает данные на носителе. Он не заменяет TLS для удалённых соединений, контроль доступа к работающему процессу, безопасные резервные копии, обновления ОС и проверку уязвимостей.

## Локальное распознавание лица при проходе

Для детекции лица и получения настоящего 128-мерного биометрического вектора используются локальные YuNet + SFace. Установите модели:

```powershell
python scripts/download_models.py
python scripts/download_face_models.py
```

Модели загружаются отдельно, не коммитятся в Git, а SHA-256 проверяется скриптом. Шаблоны сотрудников и фотографии шифруются AES-GCM поверх SQLCipher. При считывании NFC UID запускается случайная последовательность активной liveness-проверки; затем сервер сравнивает вектор с активными шаблонами, проверяет порог и разницу между лучшим и вторым совпадением. Неизвестное, неоднозначное лицо или лицо, не соответствующее карте, получает отказ. Только после этого решение передаётся в AccessPolicy и журнал.

**Ограничения перед production:** каталог OpenCV Zoo указывает Apache-2.0, но вопросы о происхождении обучающих данных и применимости лицензии к отдельным весам SFace обсуждаются upstream; перед коммерческим/производственным использованием нужна юридическая проверка. Порог cosine similarity — инженерная настройка, не вероятность личности; до реального применения необходимо проверить FAR/FRR на репрезентативной выборке и откалибровать пороги под конкретную камеру.

Существующие старые профили с одними MediaPipe landmarks не являются SFace-шаблонами. Их нужно перерегистрировать; система не будет выполнять идентификацию по старым геометрическим данным.


## Контроллер двери и защищённый аудит

Для запуска backend теперь нужен отдельный ключ цепочки аудита. Сгенерируйте три независимых ключа в PowerShell (каждую команду выполнить отдельно):

```powershell
python -c "import secrets; print(secrets.token_hex(32))"
```

Добавьте значения в `backend/.env`:
- `SECRET_KEY` — существующий ключ SQLCipher и шифрования биометрии; не менять после создания базы.
- `AUDIT_HMAC_KEY` — отдельный ключ HMAC-цепочки аудита.
- `CONTROLLER_HMAC_KEY` — отдельный ключ AES-GCM канала контроллера.
- `CONTROLLER_ID=LESS-DOOR-01` — должен совпадать с ID прошивки.
- `CONTROLLER_ACK_TIMEOUT=4.0` — время ожидания подтверждения контроллера.

Не вставляйте ключи в Git, переписки или скриншоты. При отсутствии `AUDIT_HMAC_KEY` backend запускается в режиме блокировки операций аудита; проход не будет подтверждён. После потери ключа существующая цепочка аудита не может быть проверена.

Журнал хранится отдельно от SQLite в `backend/data/security_audit.jsonl`. Каждая запись содержит sequence, ссылку на предыдущий hash и HMAC-SHA256. Проверка доступна через `GET /api/security/audit/verify`; UI поста показывает состояние цепочки. Это tamper-evident журнал, но не аппаратное WORM-хранилище: для более сильной модели угроз нужен удалённый append-only/WORM приёмник с отдельным ключом.

Команды замку проходят по зашифрованному AES-256-GCM каналу `LESS-HW/1`. Backend принимает доступ только после корректного ACK с совпавшим nonce, подтверждённым состоянием замка и показанием датчика двери. При отсутствии совместимой прошивки/датчика доступ закрывается. Спецификация кадра, полей и требований к микроконтроллеру находится в [CONTROLLER_PROTOCOL.md](CONTROLLER_PROTOCOL.md).

Важно: в этом изменении реализована backend-сторона протокола и интерфейс статуса. Совместимая прошивка микроконтроллера, физическое подключение реле/датчика и испытания на реальном оборудовании ещё требуются. Существующие текстовые UID строки NFC-ридера остаются незашифрованными; для полной защиты UID считыватель должен передавать события через тот же защищённый контроллер.
