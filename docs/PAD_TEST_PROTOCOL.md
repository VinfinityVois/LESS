# Протокол испытаний liveness / Presentation Attack Detection (PAD)

Документ предназначен для контролируемых испытаний LESS. Текущая проверка liveness — challenge-response эвристика на MediaPipe FaceLandmarker; она не является сертифицированным PAD.

## 1. Цель

Оценить, насколько текущий сценарий пропускает bona fide пользователей и обнаруживает заранее определённые presentation attacks. Испытания не должны проводиться на реальных точках доступа или с подключённым исполнительным замком. Использовать тестовую учётную запись, тестовую карту и изолированный стенд.

## 2. Матрица испытаний

Для каждого типа провести серию независимых попыток. Внутри серии менять случайный challenge, расстояние, угол и освещение.

| Класс | attack_type | Сценарий |
|---|---|---|
| Bona fide | пусто | Живой участник выполняет все действия challenge |
| Attack | printed_photo | Распечатанная фотография лица |
| Attack | phone_photo | Фотография на смартфоне/планшете |
| Attack | screen_video | Предварительно записанное видео на экране |
| Attack | live_replay | Повторная подача ранее записанной последовательности кадров |
| Attack | partial_mask | Частичное перекрытие лица |
| Attack | static_mask | Реалистичная маска, если доступна и испытание безопасно |
| Attack | challenge_replay | Повтор ранее использованного challenge/proof |
| Attack | wrong_sequence | Действия выполнены не в запрошенном порядке |
| Attack | multi_face | В кадре два и более лица |

Для каждого сценария дополнительно проверять нормальное и слабое освещение, очки, боковой угол, движение камеры, нестабильный FPS и потерю кадров. Не объединять разные attack_type в одну категорию.

## 3. Процедура

1. Подготовить тестовый профиль и подтвердить согласие участника, если используются реальные лица.
2. Убедиться, что стенд не управляет физическим замком.
3. Запустить новый challenge. Записать случайный идентификатор испытания, тип устройства/камеры и условия.
4. Выполнить bona fide или attack-сценарий.
5. Зафиксировать фактический исход: accepted=true, только если система вернула успешную проверку; accepted=false, если система отказала.
6. Для challenge_replay повторно отправить уже использованный challenge/proof и проверить, что он отклонён.
7. Записать причину отказа без кадров, эмбеддингов, имён, NFC UID и иных прямых идентификаторов.
8. Повторить испытания для всех комбинаций сценариев и условий.

Результат одного испытания — одна строка в CSV. Не записывать в CSV фотографии, видео, base64, биометрические шаблоны, ФИО или номера карт.

## 4. Метрики

- APCER = число принятых атак / число атак данного типа.
- BPCER = число отклонённых bona fide попыток / число bona fide попыток.
- ACER = (APCER + BPCER) / 2; использовать только как сводную метрику, не скрывая значения по видам атак.
- Для APCER/BPCER рассчитывать доверительные интервалы Уилсона.
- Публиковать количество попыток вместе с каждой метрикой. Ноль ложных допусков на малой выборке не означает нулевой риск.

## 5. Формат данных

CSV заголовок:

    class,accepted,attack_type,test_condition,camera_label,failure_reason,trial_ref

- class: bona_fide или attack.
- accepted: true или false.
- attack_type: обязателен для attack, пуст для bona_fide.
- test_condition: например bright, low_light, side_angle.
- camera_label: обезличенный код камеры/модели.
- failure_reason: короткий код результата без персональных данных.
- trial_ref: случайный идентификатор испытания, не связанный с личностью.

Запуск отчёта из папки backend:

    python scripts/evaluate_pad_trials.py path\to\pad_trials.csv --output path\to\pad_report.json

## 6. Критерии и ограничения

- Сначала провести пилотную серию, затем расширить объём; не объявлять систему безопасной по нескольким попыткам.
- Сохранять результаты отдельно по attack_type, камере и условиям.
- Не менять пороги liveness автоматически на основании отчёта.
- Не считать успешный тест на фото доказательством защиты от видео, масок, deepfake или неизвестных атак.
- Если модель отсутствует, кадр повреждён, обнаружено несколько лиц или проверка недоступна, сценарий должен завершаться отказом, а не успешным проходом.
- Результаты операторских испытаний должны проверяться вторым ответственным лицом перед использованием в ВКР или эксплуатационной документации.

## 7. Что пока не автоматизировано

CLI анализирует экспертно размеченные результаты, но не генерирует фото/видео-атаки и не управляет камерой. Реальные сценарии предъявления выполняются вручную на изолированном стенде. Для автоматизированного воспроизводимого стенда понадобится отдельный генератор тестовых видеопотоков и безопасный mock camera input, не подключённый к рабочему контуру доступа.
