# План испытаний LESS: белый, серый и чёрный ящики

Дата: 11.11.2026  
Область: локальная СКУД LESS, FastAPI, SQLite/SQLCipher, камера, SFace, liveness/PAD, гостевые пропуска, журнал и операторский интерфейс.

## 1. Модели тестирования

| Подход | Что известно тестировщику | Что проверяем |
|---|---|---|
| Чёрный ящик (black-box) | Только интерфейс, API-контракт и ожидаемое поведение | Пользовательские сценарии, ошибки, роли, граничные значения, отказоустойчивость |
| Серый ящик (gray-box) | Контракты, конфигурация, схема БД и часть архитектуры | Состояния challenge, архивы, привязка субъекта, транзакции, rate limit |
| Белый ящик (white-box) | Исходный код, алгоритмы и внутренние структуры | Ветвления, исключения, токен-бакет, криптография, аудит, покрытие кода |

Это не взаимоисключающие типы. Один сценарий может проходить в нескольких моделях.

## 2. Дополнительные виды испытаний

- Функциональные и сценарные — корректное выполнение требований.
- Интеграционные — API ↔ сервисы ↔ SQLCipher ↔ контроллер.
- Системные и end-to-end — полный путь оператора от регистрации до решения о доступе.
- Регрессионные — защита ранее исправленных ошибок.
- Негативные и граничные — пустые, повреждённые, слишком большие и неожиданные входные данные.
- Security testing — аутентификация, авторизация, replay, injection, утечки, rate limiting.
- Нагрузочные (load) — ожидаемая штатная нагрузка.
- Стрессовые (stress) — ограниченное приближение к пределу ресурсов и проверка восстановления.
- Spike — короткий контролируемый скачок запросов.
- Soak/endurance — длительная стабильность; выполняется отдельно на выделенном стенде.
- Fuzz/property-based — случайные и граничные входы, инварианты.
- Отказоустойчивость и recovery — потеря камеры, БД, сети, контроллера, перезапуск.
- Совместимость — разные камеры, разрешения, браузеры и ОС.
- Usability/accessibility — прокрутка, клавиатура, контраст, читаемость, сообщения ошибок.
- Биометрические испытания — FAR/FRR для face matching и APCER/BPCER для PAD.
- Физические испытания — печатные фото, экран, replay, маски и реальные условия. Не заменяются mock-тестами.

## 3. Набор данных

Файл backend/tests/fixtures/security_test_dataset.csv содержит ровно 200 синтетических сценариев:
- 20 групп сценариев × 10 вариаций;
- black-box, gray-box и white-box;
- синтетические субъекты TEST-SUBJECT-001…050;
- тестовые UID TEST-0001…0200;
- ожидаемые исходы и уровни важности.

Это тестовые записи, а не 200 реальных сотрудников или биометрических образцов. Для измерения FAR/FRR и APCER/BPCER нужны отдельные размеченные независимые наборы изображений и физических атак.

## 4. Безопасная проверка нагрузки и DDoS-устойчивости

В репозитории есть backend/scripts/safe_load_test.py — ограниченный локальный генератор нагрузки:
- только HTTP GET /api/status;
- только loopback: 127.0.0.1, localhost или ::1;
- не более 8 параллельных workers;
- не более 30 секунд;
- не более 300 запросов;
- не поддерживает внешние адреса, произвольные пути, POST, spoofing или amplification.

Запуск на локальном стенде:

```powershell
cd backend
python scripts/safe_load_test.py --duration 10 --concurrency 4 --max-requests 120
```

Ожидаемые признаки:
- штатные запросы получают 200;
- при превышении token bucket часть запросов получает 429 и Retry-After;
- процесс backend продолжает отвечать после снижения нагрузки;
- память таблицы лимитера ограничена 4096 ключами;
- Content-Length больше 12 MiB отклоняется кодом 413.

Это не DDoS-атака и не сертификация защиты от распределённой атаки. Реальные DDoS, сетевые flood, тестирование внешних IP и стрессование чужих сервисов запрещены в этом сценарии. Для полноценного red-team теста нужна письменная авторизация, отдельный стенд, согласованный профиль нагрузки и план остановки.

## 5. Запуск автоматических тестов

Из корня репозитория:

```powershell
$env:PYTHONPATH = "backend"
python -m unittest discover -s backend/tests -v
cd frontend
npm ci
npm run build
```

Тесты с камерой и физическими атаками должны выполняться отдельно на оборудовании. Unit tests и синтетические данные не доказывают качество реального PAD.

## 6. Критерии выхода

1. Все unit и integration tests проходят.
2. Frontend TypeScript build проходит без ошибок.
3. Нет критических/high security findings без принятого решения.
4. Rate limit и request-size guard подтверждены локальным тестом.
5. Гостевой архив сохраняет историю при истечении, исчерпании и ручном удалении.
6. Повторный liveness challenge не переиспользует proof и не меняет пользователя/оператора.
7. Камера выдерживает длительную работу без накопления RAF, потоков и объектов MediaPipe.
8. Для биометрических метрик представлены отдельные размеченные данные, условия и доверительные интервалы.

## 7. Ограничения текущего этапа

- Встроенный token bucket действует в памяти одного процесса. Для нескольких worker/process/узлов нужен общий лимитер (например Redis) и согласованная политика доверия к reverse proxy.
- Ограничение размера тела проверяет Content-Length; для недоверенного reverse proxy дополнительно требуется лимит на уровне ASGI ingress/proxy и потоковое ограничение чтения.
- Без физического стенда нельзя делать вывод об устойчивости к печатным фото, replay, маскам и deepfake.
