# План развития биометрии и интеллектуальной аналитики LESS

Ветка: feat/biometric-ai-analytics

## Принципы

1. ИИ не управляет замком. Решение о доступе остаётся за детерминированной политикой LESS и подтверждённым ответом контроллера.
2. Каждый вывод объясним: для предупреждения сохраняются факторы, связанные события, версия модели и оценка уверенности.
3. Fail-safe: недоступность ML/LLM не должна блокировать штатную проверку доступа и не должна разрешать проход.
4. Локальная обработка по умолчанию. Биометрия, журналы и служебные данные не отправляются внешним AI API.
5. Измеряем качество. Нельзя заявлять FAR/FRR, точность PAD или качество обнаружения аномалий без воспроизводимого набора испытаний.
6. Разделяем контуры: биометрия, аналитика событий и анализ исходного кода — разные задачи с разными моделями угроз.

## Направление A. Биометрия лица и PAD

### A1. Калибровка SFace

- Создать отдельный инструмент оценки, не меняющий рабочий порог автоматически.
- Собирать пары genuine/impostor с метками и идентификаторами тестовых сессий; не включать реальные персональные данные в репозиторий.
- Рассчитывать ROC/DET, FAR, FRR, TAR при заданных FAR, EER и доверительные интервалы.
- Проверять порог отдельно по условиям: освещение, угол, расстояние, камера, очки и качество кадра.
- Сравнивать результаты с текущим порогом SFace 0.363 и сохранять отчёт о выбранном пороге.
- Не считать similarity score вероятностью совпадения.

### A2. Испытания liveness / PAD

Сформировать тестовый протокол для живого пользователя, печатной фотографии, фотографии на другом устройстве, воспроизведения видео на экране, повторного предъявления ранее записанной последовательности, частичного перекрытия лица, попыток обмана движениями, плохого освещения, движения камеры и потери кадров.

Измерять APCER/BPCER и отдельно учитывать ошибки камеры/качества кадра. Текущую challenge-response эвристику не называть сертифицированной PAD.

### A3. Отпечаток пальца

- Сначала определить совместимый сканер, SDK/драйвер и лицензионные ограничения.
- Ввести интерфейс адаптера биометрического устройства, чтобы не привязывать бизнес-логику к одному производителю.
- Хранить только защищённый шаблон в согласованном формате; исключить хранение исходных изображений отпечатка без отдельной необходимости.
- Добавить регистрацию, проверку качества, удаление/перерегистрацию, аудит и тесты отказа устройства.
- До выбора модели сканера не заявлять совместимость с конкретным оборудованием.

## Направление B. Интеллектуальная аналитика событий

Сохранить текущий AIAnalyzer как прозрачный Rule-Based слой. Рядом построить независимый ML-контур:

1. Нормализация событий доступа, состояния двери/контроллера и отказов биометрии.
2. Агрегация признаков по пользователю, двери и временным окнам.
3. Isolation Forest как первый экспериментальный unsupervised baseline (scikit-learn уже присутствует в backend requirements).
4. Поведенческие профили только при достаточной истории и с учётом смен, отпусков и временных разрешений.
5. Объяснимый risk score, объединяющий правила и ML-сигналы.
6. Дедупликация и корреляция событий в единый инцидент.
7. Интерфейс оператора: почему сработало, какие события связаны, модель/версия, время, статус проверки.

ML-оценка — сигнал для оператора или дополнительной проверки, а не самостоятельный запрет/разрешение доступа. При недостатке данных модель должна возвращать insufficient_data, а не выдумывать оценку.

### Первичные сценарии

- серия отказов по одной карте или одному субъекту;
- одна карта используется в разных точках за физически неправдоподобный промежуток;
- необычная последовательность дверей;
- резкое изменение времени/частоты проходов;
- повторяющиеся ошибки liveness или биометрического сопоставления;
- расхождение команд и телеметрии двери;
- подозрительные события контроллера: held-open, forced-open, потеря связи, повтор ACK/nonce.

### Метрики

Для размеченных сценариев: precision, recall, F1, false-positive rate, PR-AUC и задержка обработки. Для неразмеченных данных: доля проверенных оператором тревог, число ложных тревог на пользователя/дверь/день и стабильность по периодам. Отчёты должны фиксировать размер выборки и ограничения.

## Направление C. ИИ-помощник оператора

Отдельный помощник может объяснять предупреждение обычным языком со ссылкой на конкретные события, строить краткую хронологию инцидента, отвечать на вопросы по документации LESS и регламентам, предлагать оператору список проверок и черновик отчёта, группировать похожие инциденты.

Предпочтительная последовательность: сначала локальный поиск и шаблонные объяснения; затем — локальная LLM с RAG по разрешённым документам. Внешний API не использовать для биометрии, персональных данных и полного журнала. Все ответы помощника помечать как рекомендации, требовать подтверждения оператора для действий и защищать от prompt injection в текстах журналов/документов.

## Направление D. Анализ ошибок и уязвимостей самого LESS

Это отдельный DevSecOps-контур, а не анализатор проходов:

- статический анализ Python (Bandit) и TypeScript/JavaScript (ESLint security rules);
- аудит зависимостей Python и npm (pip-audit, npm audit);
- поиск секретов и случайно закоммиченных ключей;
- SAST/CodeQL или Semgrep для потоков ввода, авторизации, криптографии и API;
- тесты на некорректные входные данные, гонки, повтор запросов, replay, отказ оборудования и обход RBAC;
- анализ SBOM и лицензий зависимостей;
- отчёт с severity, CWE/CVE, затронутым файлом/строкой, доказательством и рекомендацией.

LLM может суммировать подтверждённые результаты сканеров и помогать разбирать код, но не должна объявлять уязвимость доказанной без воспроизводимого подтверждения. Нельзя автоматически менять код, ключи, права или конфигурацию безопасности без review.

## Очерёдность реализации

1. Тестовый протокол и evaluator для SFace: FAR/FRR/ROC без изменения production-порога.
2. PAD test harness и отчёт по атакам предъявления.
3. ML anomaly baseline с проверкой достаточности данных, объяснениями и тестами.
4. Корреляция событий и риск-оценка с дедупликацией инцидентов.
5. DevSecOps-сканирование в CI и единый отчёт уязвимостей.
6. Абстракция fingerprint reader; конкретный адаптер после выбора устройства.
7. Операторский AI-помощник после появления проверяемой базы инцидентов и документации.

## Критерии готовности

- Рабочий контур доступа не зависит от доступности ML/LLM.
- Модели не получают секреты, ключи или неограниченный доступ к БД.
- Все результаты анализа имеют происхождение и воспроизводимые тесты.
- Нет автоматического изменения production-порогов на основании неподтверждённых данных.
- В README и ВКР чётко разделены реализованные функции, экспериментальные прототипы и планы.


## Фактический статус реализации в feat/biometric-ai-analytics

### Реализовано в коде этой ветки
- SFace evaluator: FAR/FRR/TAR, ROC curve, ROC AUC, приближённый EER, Wilson 95% intervals и offline threshold recommendation.
- PAD evaluator и отдельная UI-лаборатория: камера, challenge-response, классы bona fide/attack, тип атаки, фиксация результата без сохранения кадров, APCER/BPCER/ACER и разрез по типу атаки, камере и условиям съёмки.
- Isolation Forest baseline: агрегированные профили по субъектам, 30-дневное окно по умолчанию, минимум 12 субъектов и 3 события на субъекта; пороги конфигурируются.
- Incident correlation: правила + ML-сигналы, дедупликация, эвристический risk score, хранение доказательств и статусы обработки.
- UI центра инцидентов: фильтры, факторы риска, связанные события, обработка/отклонение и вызов локального помощника.
- DevSecOps CI: Bandit, Semgrep report, Gitleaks, pip-audit и npm audit.
- Fingerprint adapter contract: интерфейс устройства и fail-closed поведение без подключённого сканера.
- Local AI Assistant: read-only объяснение карточки инцидента через Ollama-compatible loopback runtime; отключён по умолчанию.
- Обновлён экран входа LESS: responsive secure gateway, доступность полей и состояния ошибок.

### Что пока НЕ подтверждено испытаниями
- FAR/FRR/ROC на реальной репрезентативной выборке SFace. Evaluator готов, но размеченный датасет должен быть подготовлен и испытан.
- APCER/BPCER на реально проведённых атаках. PAD-лаборатория записывает только результат ручного сценария и метаданные; она не генерирует автоматически фото/видео/replay и не доказывает сертификацию PAD.
- Полезность Isolation Forest на данных эксплуатации, точность тревог и устойчивость по периодам. Модель экспериментальная, score относительный, не вероятность.
- Фактическая работа LLM-помощника: нужен установленный Ollama runtime и модель. Пока LOCAL_LLM_ENABLED=false.
- Физическая регистрация и проверка отпечатка: нужен выбранный совместимый сенсор и vendor SDK. Текущий adapter contract не является работающим фактором доступа.
- Результаты текущего CI должны проверяться в GitHub Actions для актуального HEAD; наличие workflow само по себе не означает успешную проверку.

### Форматы входных данных evaluator

SFace CSV (optional condition/camera columns produce subgroup reports):
```csv
label,similarity,condition,camera
genuine,0.812,bright,cam-a
genuine,0.901,bright,cam-a
impostor,0.244,bright,cam-a
impostor,0.361,bright,cam-a
```

Команда:
```powershell
cd backend
python scripts/evaluate_face_threshold.py .\scores.csv --target-far 0.001 --output .\face-report.json
```

PAD CSV:
```csv
class,accepted,attack_type
bona_fide,true,
bona_fide,false,
attack,false,printed_photo
attack,true,screen_video
```

Команда:
```powershell
cd backend
python scripts/evaluate_pad_trials.py .\pad-trials.csv --output .\pad-report.json
```

Не добавляйте в репозиторий фотографии, видеозаписи, биометрические шаблоны, имена или реальные UID. В отчёты передавайте только размеченные similarity scores и исходы испытаний.

### Локальный AI-помощник

1. Установить Ollama локально и загрузить модель: `ollama pull qwen2.5:3b`.
2. В backend/.env установить `LOCAL_LLM_ENABLED=true`, `LOCAL_LLM_BASE_URL=http://127.0.0.1:11434`, `LOCAL_LLM_MODEL=qwen2.5:3b`.
3. Перезапустить backend и проверить `GET /api/ai/assistant/status`.
4. В центре инцидентов использовать объяснение по конкретной карточке.

Внешние адреса LLM отклоняются. Модель получает только ограниченную структурированную карточку инцидента, не получает биометрические кадры, шаблоны, ключи, raw NFC UID или доступ к инструментам управления.


## Фактический статус реализации в ветке feat/biometric-ai-analytics

Статус сверён с исходниками ветки. Наличие модуля не означает, что функция прошла эксплуатационные испытания.

| Этап | Реализация в коде | Что ещё требуется |
|---|---|---|
| 1. SFace evaluator | Реализованы FAR/FRR/TAR, Wilson CI, ROC/AUC, SVG-график, группировка по условиям и камерам, CLI и unit-тесты | Собрать корректно размеченные genuine/impostor score на согласованной выборке; оценить доверительные интервалы и отдельно утвердить порог |
| 2. PAD / liveness | Есть evaluator APCER/BPCER/ACER, разбивка по видам атак/условиям/камерам и CSV CLI | Провести физические испытания фото, экранного видео, replay и иных атак; текущая статистика не доказывает устойчивость PAD |
| 3. ML anomaly detection | Есть экспериментальный Isolation Forest, извлечение признаков, минимальные требования к объёму истории и статус insufficient_data | Проверить качество на размеченных сценариях, ложные тревоги, дрейф и стабильность по периодам; модель пока обучается в памяти на текущей когорте |
| 4. Корреляция / Risk Score | Есть корреляция правиловых и ML-сигналов, объяснимые факторы, дедупликация и сохранение версии модели в доказательствах инцидента | Калибровать эвристические веса, проверить временные окна и дедупликацию на сценариях; балл 0–100 не является вероятностью |
| 5. Security Scanner | CI включает Bandit, Semgrep (отчёт best-effort), Gitleaks, pip-audit и npm audit | Разобрать все findings, закрепить версии/правила, определить политику triage и устранить подтверждённые проблемы |
| 6. Fingerprint | Есть vendor-neutral Protocol/Service, закрепление ожидаемого device ID и fail-closed проверки ответа/challenge | Выбрать физический сканер и SDK, реализовать конкретный адаптер и пройти аппаратные испытания; реального адаптера пока нет |
| 7. Local AI Assistant | Есть read-only интеграция с локальным Ollama-compatible runtime, ограничение loopback, ограниченный контекст инцидента и тесты | Установить локальную модель, проверить prompt injection, качество объяснений и права доступа; по умолчанию помощник выключен |

### Ограничения отчётов

- ROC/AUC и FAR/FRR оценивают только переданные пары score. Разделение на genuine/impostor должно исключать утечку между train/calibration/test сессиями и учитывать повторные измерения одного человека.
- При нуле наблюдаемых ошибок FAR не равен доказанному нулю риска; верхняя граница доверительного интервала остаётся ненулевой.
- APCER/BPCER рассчитываются по экспертно размеченным испытаниям. CSV не запускает атаку на камеру автоматически.
- Isolation Forest — экспериментальный baseline, а не доказательство нарушения и не основание для автоматического отказа в доступе.
- Security Scanner может давать ложноположительные и ложноотрицательные результаты; каждый finding требует triage.
- Local LLM не получает биометрические шаблоны, NFC UID, секреты, прямой доступ к БД или операционные инструменты.
